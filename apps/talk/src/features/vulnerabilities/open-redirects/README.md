# Open Redirect

Слайды: `/talk/open-redirects/0`–`/2`. Демо: `/site/redirect`.

- `get-redirect-target.ts`: принимает пользовательский адрес без проверки origin.
- `fixed-get-redirect-target.ts`: разбирает URL, разрешает только origin магазина.
- `OpenRedirectDemo.tsx`: письмо с настоящей ссылкой, выбор и редактирование next.
- `RedirectLanding.tsx`: выбирает реализацию по режиму и вызывает window.location.assign.
- `destinations.ts`: адреса двух локальных страниц и отдельное ограничение стенда.
- `attacker.html`: внешняя учебная страница без форм и сбора данных.
- `redirect.test.ts`: адреса, нормализация URL и ограничения локального стенда.

Внешняя страница обслуживается общим `scripts/csrf-attacker.mjs` на порту
`CSRF_ATTACKER_PORT` (3001). Входная ссылка ведёт на магазин (3000), затем браузер
реально меняет origin. Исправление выполняется на фронтенде перед навигацией.
Адрес берётся из разобранного query; повторного decodeURIComponent нет.
Проверяем origin у объекта URL и используем его же href для навигации.

Ограничение стенда независимо от защиты: даже vulnerable не переходит на реальные
внешние сайты, javascript: или произвольные локальные маршруты. Разрешены только
внешняя `/redirect-offer?shopPort=...` и внутренняя `/site/redirect/order`.
В слайде показана именно разница проверки origin, не этот ограничитель.

Неверный URL, отсутствующий/повторный next и запрещённый origin показывают отказ.
Сброс письма возвращает внешний вариант. Смена режима сохраняет редактируемый next.
Возврат с внешней страницы ведёт к письму; Escape/«К слайду» внутри магазина ведут к `/talk/open-redirects/2`.

Это не демонстрация кражи cookie: порты одного хоста cookie не разделяют, но
локальный сервер их не читает, не пишет в логи и не собирает учётные данные.
В реальном приложении нельзя считать любой внутренний маршрут безопасным:
при необходимости ограничивайте назначения явным списком или идентификаторами.
Если редирект делает сервер через Location, проверку нужно делать там же.
