[сценарий докладчика](../../demo/prototype-pollution.md),

## Механизм

JavaScript ищет отсутствующее собственное свойство в цепочке прототипов.
Если недоверенные данные позволяют записать поле в Object.prototype, это значение
могут прочитать другие объекты, наследующие этот прототип. Собственные поля могут
его перекрыть; объекты с null-прототипом не наследуют Object.prototype.

В нашем примере импортируются настройки сортировки и размера страницы каталога.
Уязвимый рекурсивный merge не различает собственные вложенные объекты и прототип:
`target['__proto__']` уже существует, поэтому следующий вызов merge пишет прямо в него.
Путь `constructor.prototype` также ведёт к общему прототипу обычного объекта.

```json
{
  "view": { "sort": "price", "pageSize": 20 },
  "__proto__": { "deliveryFee": 0 }
}
```

После слияния отдельный расчёт получает новый пустой объект и читает
`deliveryOptions.deliveryFee ?? 490`. Получается 0, хотя собственное поле не задано:
`Object.hasOwn(deliveryOptions, 'deliveryFee')` возвращает false.
Это влияние на предварительную цифру во фронтенде, не на цену заказа в бэкенде.

## Важные различия

- JSON.parse создаёт собственный ключ `__proto__`, сам по себе не загрязняя прототип.
- Литерал JavaScript `{ __proto__: value }` имеет специальную семантику и не эквивалентен
  JSON.parse с таким же текстом. В payload демонстрации используется именно JSON.
- `Object.assign({}, parsed)` с собственным ключом `__proto__` может изменить прототип
  целевого объекта. Это не означает, что Object.prototype и все другие объекты изменены.
- Рекурсивное слияние или запись по нескольким динамическим ключам может достичь общего
  прототипа. Именно такое слияние реализовано в учебном модуле.
- Наличие свойства `isAdmin` в объекте браузера не создаёт серверных прав.
  XSS, обход доступа и выполнение кода требуют дополнительного уязвимого потребителя.

## Исправление

В приложении с известным форматом настроек нет необходимости принимать произвольные
поля и пути. Используем Zod: строгая схема разрешает только `view.sort` и
`view.pageSize`, проверяет типы и отклоняет лишние ключи на обоих уровнях.
После успешной валидации два поля копируются явно, рекурсивного слияния нет.

Файлы пары:
[уязвимый merge](../../../apps/talk/src/features/vulnerabilities/prototype-pollution/merge-catalog-settings.ts),
[исправленный импорт](../../../apps/talk/src/features/vulnerabilities/prototype-pollution/fixed-merge-catalog-settings.ts).

Для словарей могут подойти Map или Object.create(null). Для чтения необязательных
опций полезно различать собственные и унаследованные поля через Object.hasOwn.
Это дополнительные меры, а не разрешение использовать небезопасный merge где угодно.
Обновление уязвимой сторонней библиотеки остаётся обязанностью приложения-потребителя.

Доверенные решения о цене и доступе принимает сервер на основании проверенных данных.
Блокировка только слова `__proto__` недостаточна, если остаётся проход через
`constructor.prototype` или другой путь к прототипу.

## Проверка

Демо запускает слияние и независимый расчёт в новом Web Worker. Там изменение
Object.prototype настоящее; React и сервер имеют другие JavaScript-контексты.
Изоляция нужна стенду, а исправлением остаётся строгий импорт.

Тесты проверяют оба пути атаки, вложенный payload, отсутствие загрязнения после
одного JSON.parse, чтение унаследованного свойства, неизменность собственных полей,
отказ до записи в fixed, валидный импорт, сброс и чистоту прототипа страницы.
Исправление источника не отменяет уже сделанное загрязнение: каждый повторный прогон
демо использует новый контекст, а не пытается исправить общий прототип на месте.
