# Сторонние скрипты: пример с чатом

`pnpm dev` поднимает магазин на `127.0.0.1:3000` и поставщика/получателя на
`127.0.0.1:3001`. Порты: `TALK_PORT`, `CSRF_ATTACKER_PORT`. Все обращения локальные.

## Сценарий доклада

1. `/talk/third-party-scripts/0`: общий риск подключения стороннего JavaScript.
   Аналитика, реклама, библиотеки с CDN и виджеты выполняются в контексте нашего сайта.
   Чат и инцидент Ticketmaster / Inbenta (2018) — только пример этого класса угроз.
2. `/1`: контроль кода и обновлений, SRI для статичных файлов, CSP и изоляция
   независимых виджетов. У каждой меры свои границы. HttpOnly и отключение
   скрипта только на checkout не защищают сайт от уже исполняемого чужого кода.
3. `/2`: сверху наш код. В fixed на checkout возвращаем null и не добавляем script.
   Снизу одинаковый в обеих вкладках фрагмент, который атакующий добавил в файл чата.
   Текущий fixed — локальная мера для этого примера, а не полное исправление угрозы.
4. `/3`: открыть демо с вариантом «Подменённый». Email и адрес уже появились у
   получателя, хотя «Оформить заказ» ещё не нажимали.
5. Нажать «Когда доставят заказ?»: чат отвечает, видимая функция не сломалась.
6. Выбрать «Исходный»: чат работает, данных нового запуска у получателя нет.
7. Переключить «Исправлено»: скрипт чата не загружается, остаётся свой контакт
   поддержки. Нажать «Оформить заказ»: учебный заказ оформляется без виджета.
8. Сбросить сценарий; вернуться к слайду через Escape или кнопку.

В Network уязвимого запуска видны GET `support-chat.js` и POST `/third-party/collect`.
В fixed нет обоих запросов; GET `/third-party/captures` делает наш учебный монитор.
Это не исправление кода поставщика, а изменение нашей интеграции.

## Ограничения

Демо показывает механизм, не способ первоначального взлома поставщика. Поля
предзаполнены вымышленными данными, readOnly; карты и платежи отсутствуют.
Получатель принимает только эти значения, не читает cookie, ограничивает хранение.
Каждая смена режима/варианта и сброс создают новый UUID. Старые отправки не отменяются.
Сброс с подменённым файлом в уязвимом режиме повторяет утечку.

Удаление уже загруженного script не отменяет произвольные эффекты чужого JS.
В реальной SPA нужно исключить попадание внешнего кода на чувствительную страницу
и при переходах, а не только проверять путь в момент загрузки. Здесь виджет живёт
только в checkout, а его известные эффекты очищаются при размонтировании.
SRI и sandbox/iframe не реализованы. CSP совместима с Next dev, не production-рецепт.

Источник реального кейса: [решение ICO по Ticketmaster](https://ico.org.uk/media/action-weve-taken/mpns/2618599/ticketmaster-uk-limited-mpn.pdf).

[MDN: script-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src).
