# Сторонние скрипты: пример подмены файла

`pnpm dev`: магазин на `127.0.0.1:3000`, поставщик/получатель на `127.0.0.1:3001`.
Порты: `TALK_PORT`, `CSRF_ATTACKER_PORT`. Все обращения и данные учебные, локальные.

## Сценарий доклада

1. `/talk/third-party-scripts/0`: аналитика, реклама, библиотеки с CDN и виджеты
   выполняют код в контексте нашего сайта. Чат — пример, не отдельный класс угроз.
2. `/1`: контроль обновлений, SRI, CSP, изоляция виджетов и границы каждой меры.
   HttpOnly не мешает коду выполнять запросы от имени пользователя. Отключение
   скрипта только на checkout не защищает от его запуска на главной.
3. `/2`: сверху наше подключение. Fixed всегда выставляет integrity по проверенной
   версии до добавления script в DOM. В нём нет pathname и исключений для главной.
   Снизу один и тот же добавленный атакующим фрагмент; код поставщика мы не правим.
4. `/3`: открыть демо на главной. Подменённый скрипт уже отправил email и адрес.
   В заказ ещё не переходили. Чат по-прежнему отвечает на вопрос о доставке.
5. Переключить «Исправлено»: открывается новый документ. Файл скачивается, но
   браузер отклоняет его по SRI до выполнения. Чат не появляется, новой утечки нет.
6. Выбрать «Исходный»: проверенный чат проходит SRI и работает, данные не уходят.
7. Перейти к оформлению. Проверка та же: подменённый файл не выполняется, исходный
   работает. Сам заказ можно оформить независимо от доступности чата.
8. Сбросить запуск, вернуться через Escape или кнопку. Сброс сохраняет вариант файла.

В Network подменённого vulnerable-запуска есть GET `support-chat.js` и POST
`/third-party/collect`. В fixed остаётся GET скрипта, но нет выполнения и POST.
Консоль показывает несовпадение integrity. GET `/third-party/captures` делает наш
монитор. Сетевые ошибки тоже вызывают script.onerror, потому UI не называет любое
отклонение загрузки доказательством подмены. Браузерные тесты различают эти случаи.

## Границы

Хеш сохранён заранее по проверенному файлу, не взят из текущего ответа CDN.
SRI работает здесь для статичной версии и защищает от изменения её байтов.
Проверять поведение и обновления всё равно нужно; хеш вредоносной версии её
не обезвредит. Вложенные ресурсы не защищаются автоматически. Сервер разрешает
CORS; script использует anonymous. CSP позволяет локальный источник в обоих
режимах, поэтому блокировка в fixed происходит именно из-за хеша.

Защита должна действовать с первого подключения. SRI не отменяет уже исполненный
код и прошлую утечку: смена режима начинает новый документ с новым UUID.
Удаление тега не является откатом исполнения. В демо не моделируется восстановление
после компрометации. Форма readOnly, получатель принимает только два значения и не читает cookie.

Реальный пример: [решение ICO по Ticketmaster / Inbenta](https://ico.org.uk/media/action-weve-taken/mpns/2618599/ticketmaster-uk-limited-mpn.pdf).
Демо не реконструирует первоначальный взлом поставщика.
Источники по мерам: [MDN: SRI](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Subresource_Integrity),
[OWASP: сторонний JavaScript](https://cheatsheetseries.owasp.org/cheatsheets/Third_Party_Javascript_Management_Cheat_Sheet.html).
