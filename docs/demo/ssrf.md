# SSRF

Начало: `/talk/ssrf/0`. Демо: `/site/backend/ssrf`.

## Сценарий доклада

Основа: Cybersecurity.pptx, слайд 12. Покажите обычный каталог в обоих режимах, затем внутренний URL: vulnerable возвращает зарплатную ведомость, fixed отвечает 403 до HTTP-запроса. Отдельно проверьте редирект поставщика. lab-network.ts выполняет реальные HTTP-запросы к loopback-серверу на случайном порту. Имена .test обозначают роли в условной сети и не резолвятся через настоящий DNS. Стенд принимает только три подготовленных адреса в обоих режимах, не обращается к интернету, metadata или LAN. Это страховка лаборатории, а не исправление. В обычной инфраструктуре адрес поставщика нужно разрешать через контролируемый DNS/egress, исключая rebinding и нежелательные IP. Для URL-preview с произвольными доменами требуется другая, более общая политика. Сервис недоступен через обычную форму импорта в fixed, хотя преподаватель на этой же машине может открыть loopback напрямую.

## Код

Серверная пара в `apps/talk/src/features/vulnerabilities/ssrf`:
`import-catalog.ts` и `fixed-import-catalog.ts`.
Слайд читает эти же файлы. API: `POST /api/site/backend/ssrf`.

## Общие границы лаборатории

- Только вымышленные данные. Не вводить реальные пароли, токены и адреса.
- Cookie `backend-lab` отделяет одну копию сценария от другой. Это инфраструктура стенда.
- Cookie `demo-mode` выбирает серверную реализацию. Параметр режима из JSON не принимается.
- Состояние существует до часа, максимум 200 активных копий на процесс. Перезапуск очищает его.
- При переключении режима и сбросе сервер начинает чистый сценарий. Ввод формы сохраняется для сравнения.
- Управляющие POST не принимают чужой Origin. JSON ограничен 4096 байтами.
- Кнопки сброса и выбора уязвимого режима не предназначены для production.
