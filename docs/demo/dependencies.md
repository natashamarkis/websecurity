# Уязвимая зависимость в карточке товара

Слайды: `/talk/dependencies/0`–`/talk/dependencies/3`. Демо: `/site/product`.

1. Показать форму магазина: она передаёт описание в компонент библиотеки.
2. Применить обычный текст и убедиться, что карточка обновилась.
3. Нажать «Подставить payload», затем «Применить описание».
4. В версии 1.0.0 появится alert «Код из зависимости выполнен». Закрыть его.
5. Переключить на «Исправлено». Версия станет 1.0.1; описание и поле сохранят тот же ввод.
6. Теперь payload виден как текст. Повторное применение не запускает код.
7. «Сбросить» возвращает исходное описание. Escape возвращает к демо-слайду.

Обе версии находятся рядом в `features/vulnerabilities/dependencies/library`.
Переключение модели: `vulnerable ? <ProductDescription /> : <FixedProductDescription />`.
Формат описания — обычный текст; поддержки rich HTML в исправленном контракте нет.
Это клиентское демо: после перезагрузки страницы описание возвращается к исходному.

## Audit и обновление

`demo-description` — локальный вымышленный модуль. Не устанавливать одноимённый
пакет из реестра. У него нет advisory: настоящий audit не найдёт учебную ошибку,
а переключатель не меняет package.json или lock-файл и не запускает npm/pnpm.

Для настоящего пакета из отчёта audit (подставить его имя и исправленную версию):

```sh
pnpm audit
pnpm why <package>
pnpm --filter @ws/talk update <package>@<fixed-version>
pnpm test
pnpm audit
```

Обновление выше относится к прямой зависимости. Для транзитивной сначала выясняем
родительский пакет и путь обновления. Проверяем изменения lock-файла, совместимость
и повторяем атаку. Audit проверяет известные уязвимости, не анализирует весь исходный
код и не гарантирует отсутствие неизвестных ошибок или вредоносного поведения.

Источники: [pnpm audit](https://pnpm.io/cli/audit), [pnpm update](https://pnpm.io/cli/update).
