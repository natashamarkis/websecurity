# Session Management: фиксация сессии

Начало: `/talk/sessions/0`. Демо: `/site/backend/sessions`.

## Сценарий доклада

Основа: Cybersecurity.pptx, слайд 13. Нажмите 1, затем 2, затем 3. Два клиента в одной панели явно моделируют уже состоявшееся навязывание анонимного ID. Это не две настоящие вкладки с разными cookie: их cookie jars хранит лаборатория на сервере. Возможные предпосылки реального навязывания: приложение принимает ID из URL или cookie planting с поддомена. Шаг 1 не утверждает, что чужой сайт может произвольно записать HttpOnly-cookie. Шаг 2 реально проверяет учебный пароль на бэке. В vulnerable ID совпадают и профиль доступен атакующему. В fixed старый ID удалён, новый виден у покупателя, ответ атакующему 401. После переключения режима сценарий начинается заново. Выход отзывает ID в обоих режимах, TTL 15 минут. Полный login-flow, password storage, доставка письма и HTTPS не входят в этот короткий сценарий. Внешняя cookie backend-lab изолирует зрителей, её нельзя путать с моделируемым Session ID.

## Общие границы лаборатории

- Только вымышленные данные. Не вводить реальные пароли, токены и адреса.
- Cookie `backend-lab` отделяет одну копию сценария от другой. Это инфраструктура стенда.
- Cookie `demo-mode` выбирает серверную реализацию. Параметр режима из JSON не принимается.
- Состояние существует до часа, максимум 200 активных копий на процесс. Перезапуск очищает его.
- При переключении режима и сбросе сервер начинает чистый сценарий. Ввод формы сохраняется для сравнения.
- Управляющие POST не принимают чужой Origin. JSON ограничен 4096 байтами.
- Кнопки сброса и выбора уязвимого режима не предназначены для production.
