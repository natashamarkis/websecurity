# Clickjacking

Запуск: `pnpm dev`. Магазин на 3000, страница-приманка на 3001.
Порты настраиваются через `TALK_PORT` и `CSRF_ATTACKER_PORT`.

## Сценарий

1. `/talk/clickjacking/0`: пользователь видит одно действие, а нажимает другое.
   Чужая страница положила прозрачный iframe с магазином поверх приманки.
2. `/1`: показать бэкенд-код заголовков и фронтенд атакующего под ним.
   В fixed меняются заголовки магазина, а не HTML атакующего.
3. `/2`: открыть демонстрацию. Уведомления включены, в почте письмо о бонусе.
4. Нажать «Открыть предложение». Во второй вкладке включить «Показать скрытый iframe»:
   над бонусом находится настоящий личный кабинет с кнопкой отключения.
5. Скрыть слой и нажать «Получить бонус». Вернуться в профиль магазина:
   уведомления отключены. Состояние перечитывается при фокусе и каждые две секунды,
   пока профиль видим; есть ручное обновление.
6. Закрыть вкладку акции. Нажать «Сбросить», выбрать «Исправлено», открыть предложение
   заново. Теперь браузер блокирует iframe. Раскрыть слой, показать отказ браузера.
   Нажатие на место бонуса не меняет уведомления.
7. «Настройки уведомлений» открывают ту же страницу напрямую. В fixed её кнопка
   продолжает работать: запрет относится к встраиванию, не к обычному пользованию.
8. Сбросить состояние, закрыть дополнительные вкладки, вернуться к слайду через Escape.

## Почему токен не спас

Это не поддельный POST с чужой страницы. Браузер отправляет настоящую форму магазина:
в ней уже есть случайный токен сессии. Origin запроса тоже принадлежит магазину.
Обе проверки работают в обоих режимах; атакующему не нужно знать токен или читать DOM.
Он знает расположение кнопки и обманывает пользователя относительно смысла клика.

## Границы защиты

`Content-Security-Policy: frame-ancestors 'none'` должен приходить HTTP-заголовком
от встраиваемого сайта. Через `<meta>` эта директива не работает. `frame-src`
управляет тем, что встраивает сама страница, а не тем, кто может встроить её.
Общая CSP стенда сохраняется; антифрейминг добавлен без потери остальных директив.
`X-Frame-Options: DENY` служит запасным совместимым запретом.

Если встраивание действительно нужно, задаётся список доверенных origin.
Для критичных операций полезна повторная аутентификация. Рассматриваем именно
iframe-based Clickjacking; атаки через отдельные окна этим примером не покрываются.

SameSite может ограничить сессию в cross-site iframe. В стенде два порта одного хоста:
origin разные, site один, поэтому SameSite=Lax не мешает демонстрации.
HttpOnly не запрещает браузеру отправлять cookie; CORS не запрещает встраивать HTML.
Cookie не изолированы портом, поэтому сервер акции их намеренно игнорирует.
Учебная настройка изолирована случайной сессией, настоящих уведомлений и аккаунтов нет.

Новые заголовки не отзывают уже загруженный iframe в старой вкладке. После смены режима
нужно заново открыть предложение: браузер проверит заголовки нового HTML-ответа.
