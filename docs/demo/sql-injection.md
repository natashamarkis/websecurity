# SQL Injection

Начало: `/talk/sql-injection/0`. Демо: `/site/backend/sql-injection`.

## Сценарий доклада

Основа: Cybersecurity.pptx, слайд 14. Обычный поиск «Кабель» даёт один свой заказ. Выберите SQL-инъекцию и отправьте: четыре заказа, включая Марию и Ивана, с адресами. Покажите выполненный SQL: комментарий -- убирает завершающую кавычку, OR 1=1 обходит фильтр владельца. В fixed та же строка передаётся параметром, чужих строк нет. Затем проверьте обычный поиск и пустую строку: свой заказ и все два своих заказа по-прежнему доступны. Работает настоящий node:sqlite, не проверка наличия payload через includes. На каждый запрос создаётся маленькая отдельная БД :memory:, query_only включён после заполнения, четыре вымышленных заказа. Пользователь alex задан сервером лаборатории, полноценная аутентификация не добавляется. Параметры не предназначены для подстановки имён столбцов или ORDER BY: такие идентификаторы выбираются из серверного списка.

## Общие границы лаборатории

- Только вымышленные данные. Не вводить реальные пароли, токены и адреса.
- Cookie `backend-lab` отделяет одну копию сценария от другой. Это инфраструктура стенда.
- Cookie `demo-mode` выбирает серверную реализацию. Параметр режима из JSON не принимается.
- Состояние существует до часа, максимум 200 активных копий на процесс. Перезапуск очищает его.
- При переключении режима и сбросе сервер начинает чистый сценарий. Ввод формы сохраняется для сравнения.
- Управляющие POST не принимают чужой Origin. JSON ограничен 4096 байтами.
- Кнопки сброса и выбора уязвимого режима не предназначены для production.
- Оболочка принимает обычный поиск до 80 символов или точный учебный payload. Произвольные SQL-программы и функции не запускаются. Это предел стенда в обоих режимах, а не замена prepared statements. Нужен Node.js 24 с node:sqlite; возможен штатный ExperimentalWarning.\n
