# CSRF: изменение адреса доставки

Запуск из корня: `pnpm dev`. Основной сайт: <http://127.0.0.1:3000>,
страница акции: <http://127.0.0.1:3001/offer>. Оба сервера слушают только loopback.
Если основной сайт уже запущен отдельно, достаточно `pnpm dev:attacker`.
Для других портов задайте `TALK_PORT` и `CSRF_ATTACKER_PORT` перед запуском.

## Показ

1. Открыть `/talk/csrf/0`, затем слайд с парой серверных обработчиков `/talk/csrf/1`.
2. На `/talk/csrf/2` нажать «Открыть демонстрацию». Откроется профиль доставки
   в режиме «Уязвимо». Сбросить данные: адрес «Москва, ул. Лесная, 10».
3. Нажать «Открыть акцию». В новой вкладке другой origin, порт 3001.
4. Нажать «Получить скидку». Обычная HTML-форма отправляет POST на основной сайт.
   Токена нет, cookie браузер добавляет сам. Ответ: HTTP 200, адрес изменён.
5. Вернуться в исходную вкладку. Профиль обновляется при фокусе; также есть кнопка
   обновления. Адрес теперь «Москва, ул. Подставная, 99», источник запроса с портом 3001.
6. Переключить на «Исправлено», нажать «Сбросить» и повторно открыть акцию.
   Тот же POST получает HTTP 403, адрес остаётся исходным.
7. В обычной форме профиля сохранить свой учебный адрес. Запрос с токеном проходит.
8. Сбросить данные. Escape или «К слайду» возвращает в CSRF-модуль.

## Механизм и ограничения

- Два порта одного хоста дают разные origin, но один site. Поэтому `SameSite=Lax`
  не блокирует cookie в этой демонстрации. Это cross-origin CSRF, не демонстрация
  обхода SameSite между разными site. Не смешивать `localhost` и `127.0.0.1`:
  ссылка на акцию автоматически сохраняет имя хоста основного сайта.
- Сервер акции статический: он не читает cookie, не исполняет внедрённый JavaScript,
  не обращается к серверному хранилищу и не читает ответ API через CORS.
  Порты не изолируют cookie; это локальная учебная модель, не схема production-хостинга.
- Профиль использует отдельную случайную HttpOnly-cookie `csrf-session` и хранится
  в памяти сервера один час. Неверная или отсутствующая сессия даёт 401 даже в
  уязвимом режиме. Учебная сессия создаётся при открытии профиля, настоящего входа нет.
- В исправленном обработчике проверяется случайный 256-битный токен, связанный
  с конкретной сессией. Клиент читает токен через same-origin запрос профиля;
  чужому origin чтение через CORS не разрешено. Токен не попадает в URL или логи.
  Ответ профиля имеет `Cache-Control: no-store`.
- Поддельная форма меняет только адрес доставки. Режим и сброс демо отдельно
  отклоняют браузерные запросы с чужим Origin.
- `fixed` здесь устраняет CSRF для операции доставки, а не все риски приложения.
  XSS в том же origin способен прочитать токен; XSS демонстрируем отдельным сценарием.

Подход основан на [OWASP: Synchronizer Token Pattern](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#synchronizer-token-pattern).

## Проверки

`pnpm test` проверяет отсутствие/ошибку/чужой токен, действительную сессию,
успешную обычную форму, неверный адрес, сброс и изоляцию профилей.
`pnpm e2e` отправляет настоящую форму с другого origin и проверяет 200/403,
автоматическую отправку cookie, переключение режима и мобильный вид.
