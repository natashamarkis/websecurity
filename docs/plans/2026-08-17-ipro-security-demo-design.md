# Дизайн: iPRO Security Demo — учебное уязвимое приложение

**Дата:** 2026-08-17
**Статус:** утверждён (объём зафиксирован), готов к планированию реализации
**Автор материалов для tech talk:** этот документ + вики на главной = точка входа для нового участника

---

## 1. Цель и аудитория

Учебное веб-приложение, которое **в узнаваемой стилистике реального продукта компании (iPRO OneTeam)** демонстрирует сотрудникам, как выглядят и как эксплуатируются типовые веб-уязвимости.

- **Аудитория:** разработчики и security-champions компании (tech talk + возможность самим потыкать).
- **Формат использования:** поднимается локально (`npm run dev`), показывается со сцены и/или человек сам заходит и абузит примеры.
- **Ключевое требование:** запуск **без VPN**, без hosts-хаков, без Docker-прокси, без приватного npm-реестра.

> ⚠️ Приложение **намеренно уязвимо** и предназначено только для локального обучения. Не деплоить в интернет, не использовать в проде.

---

## 2. Подход: «двойник», а не дословная копия

Разбор исходника `vendor-account-ui` (Vite + React + antd 5 + Redux/saga) показал:

- Вся визуальная идентичность (тема antd, палитра, типографика, **каркас** header/sider/content) приходит из **приватного** пакета `@etm/oneteam-core-ui`, плюс утилиты из `@etm/vendor-utils`. Итого **~560 файлов / 677 мест импорта**.
- Пакеты живут в `registry.etm.corp` — off-network `npm install` падает с 404. Дословная копия не соберётся, а застабить 677 мест = переписать пол-приложения. Плюс это тащит проприетарный код в демо.
- Точные бренд-цвета и логотип в исходнике **не хранятся** (внутри неустановленного пакета).
- Встроенный мок-слой (`axios-mock-adapter`) есть, но **пустой** (`combineMocks = []`) → «из коробки» приложение ходит в реальный бэкенд за VPN.

**Решение:** воссоздать «двойника» с нуля на **Next.js + публичном Ant Design 5**, повторив визуальный язык оригинала (ETM-синяя тема, русский UI, каркас «горизонтальное меню + сворачиваемый сайдбар + контент»), и встроить в него реальные уязвимости. Никаких приватных пакетов и проприетарного кода.

**Важно:** уязвимости воспроизводятся **по реально существующим в приложении паттернам** (см. §5), поэтому демо честно отражает «как это устроено у нас», а не выдуманные примеры.

## 3. Технологический стек

| Слой | Выбор | Примечание |
|---|---|---|
| Каркас | **Next.js (App Router) + TypeScript** | одно приложение = и фронт, и «бэкенд» (route handlers) |
| UI | **Ant Design 5** (публичный) | + `@ant-design/nextjs-registry` для SSR-стилей |
| Стили | **SCSS** (CSS Modules) + локальный шим токенов | воссоздаём ETM-палитру локально |
| Локаль | antd `ru_RU`, `dayjs` `ru` | интерфейс полностью на русском |
| «Бэкенд» | **Next.js Route Handlers** (`app/api/**`) | намеренно уязвимые эндпоинты |
| Хранилище | **SQLite** (`better-sqlite3`) | переживает HMR/перезапуск; нужно для stored XSS, сессий |
| Сид-данные | `@faker-js/faker` | реалистичные вендоры/заказы/статьи |

Никаких `@etm/*`, никакого внешнего API, никаких `*.etm.ru` хостов.

## 4. Структура проекта

Новый проект **заменяет** текущие `backend/` и `frontend/` в корне репозитория `websecurity`.

```
websecurity/
├── app/
│   ├── layout.tsx                 # ConfigProvider (ru + ETM-тема) + AntdRegistry
│   ├── page.tsx                   # ГЛАВНАЯ = вики уязвимостей
│   ├── (shell)/                   # аутентифицированный каркас (header + sider)
│   │   ├── layout.tsx             # HeaderMenu + Sider + Content
│   │   ├── orders/page.tsx        # экран Orders (reflected XSS)
│   │   ├── factoring/[uuid]/page.tsx   # экран Факторинг (IDOR + CSRF)
│   │   └── knowledge-base/…        # экран Базы знаний (stored/DOM XSS)
│   ├── login/page.tsx             # экран Login (open redirect + сессия)
│   └── api/                       # НАМЕРЕННО УЯЗВИМЫЙ «бэкенд»
│       ├── auth/{login,logout,session}/route.ts
│       ├── job/[uuid]/route.ts    # IDOR
│       ├── orders/route.ts        # reflected echo
│       └── articles/[id]/route.ts # stored/DOM XSS источник
├── components/                    # HeaderMenu, Sider, Logo, VulnBadge, PayloadCopy …
├── lib/
│   ├── db.ts                      # better-sqlite3 + сид
│   ├── theme.ts                   # ETM-токены antd (легко тюнить)
│   └── wiki/                       # контент вики (из docs/security-guide)
├── styles/                        # _tokens.scss (ETM-палитра), globals
├── docs/                          # СОХРАНЯЕТСЯ (security-guide, demo, plans)
├── package.json
├── next.config.ts
└── README.md                       # запуск + дисклеймер
```

`docs/` (security-guide, demo, plans) **остаётся** — это источник контента для вики и материал для tech talk.

## 5. Экраны и уязвимости (зафиксировано)

4 экрана, каждый несёт уязвимость по реальному паттерну исходника.

### 5.1 Login — Open Redirect + история сессии
- **Паттерн из оригинала:** `LoginForm` берёт `returnUrl` из query и передаёт его в `window.location.assign(returnUrl)` без allowlist; `session-id` — кука **не HttpOnly**, читается через `document.cookie`.
- **Демо:** `?returnUrl=https://evil.tld` → после «входа» редирект на произвольный домен. Плюс якорь для истории сессии (куку видно из JS → её крадёт любой XSS).
- **Уязвимости:** Open Redirect; (не-HttpOnly кука — задел для §5.3).

### 5.2 Factoring `/factoring/[uuid]` — IDOR + CSRF
- **Паттерн из оригинала:** `GET /job/:uuid` и `POST /job/:uuid/update` без проверки владельца; CSRF-токенов в приложении нет нигде.
- **Демо:** подставить/перебрать `uuid` → увидеть и отправить чужую факторинг-заявку (IDOR). Внешняя HTML-страница шлёт POST на `/job/:uuid/update` с кукой пользователя (CSRF). Есть file upload.
- **Уязвимости:** IDOR / broken access control; CSRF.

### 5.3 Knowledge Base (статья) — Stored + DOM XSS
- **Паттерн из оригинала:** единственная поверхность рендера серверного HTML (`ParsedArticle` через `html-react-parser`). В демо заменяется на `dangerouslySetInnerHTML`.
- **Демо:** тело статьи содержит `<img src=x onerror=...>` → выполняется при открытии (stored). Payload крадёт не-HttpOnly `session-id` → замыкает историю с §5.1.
- **Уязвимости:** Stored XSS; DOM XSS.

### 5.4 Orders (таблица) — Reflected XSS
- **Паттерн из оригинала:** текстовый фильтр `orderCode` эхом возвращается в UI как тег-чип (`useFilterToTag` → `TagsGroup`).
- **Демо:** ввод в поиск/фильтр отражается как чип через raw HTML → `<img src=x onerror=alert()>` срабатывает.
- **Уязвимости:** Reflected XSS.
- **Примечание:** Orders в оригинале сильнее всех завязан на приватные `Table/TagsGroup` — воссоздаём таблицу на публичном antd `Table`, это чуть больше работы (учтено в оценке).

### Итоговая матрица покрытия (6 классов — «фокус»)

| Класс | Экран |
|---|---|
| Reflected XSS | Orders |
| Stored XSS | Knowledge Base |
| DOM XSS | Knowledge Base |
| IDOR / broken access control | Factoring |
| CSRF | Factoring |
| Open Redirect | Login |

Вне объёма (сознательно): SSRF, prototype pollution, sensitive data exposure, session management (расширенно), clickjacking, insecure dependencies. Теория по ним есть в `docs/security-guide/` и может быть добавлена в вики позже как «читать далее».

## 6. Намеренно уязвимый «бэкенд» (Next.js route handlers)

| Эндпоинт | Поведение (уязвимое) |
|---|---|
| `POST /api/auth/login` | ставит куку `session-id` **без HttpOnly**, `SameSite=Lax`; принимает `returnUrl` |
| `POST /api/auth/logout` | без CSRF-токена; не чистит куку принудительно |
| `GET /api/auth/session` | регидратация пользователя по куке |
| `GET /api/job/[uuid]` | **без проверки владельца** (IDOR) |
| `POST /api/job/[uuid]/update` | state-changing, **без CSRF-токена** |
| `GET /api/orders?orderCode=…` | возвращает фильтр как есть (эхо для reflected XSS) |
| `GET /api/articles/[id]` | отдаёт HTML-тело статьи (stored/DOM XSS источник) |

Аутентификация — как в оригинале: кука `session-id` → в кастомный заголовок `Session-id`. Для наглядной CSRF-демонстрации полагаемся на автоотправку куки (в оригинале кастомный заголовок случайно даёт частичную защиту — это отметим в вики как «почему у нас пока не рвётся и как порвётся»).

## 7. Вики на главной

Главная страница — каталог из 6 карточек (по числу классов). Каждая карточка:

1. **Что это** — короткое определение (CWE/OWASP).
2. **Где «у нас»** — ссылка на реальный паттерн/файл-аналог.
3. **Как абузить** — шаги + **payload, копируемый в один клик**.
4. **Impact** — что получает атакующий.
5. **Как чинить** — конкретная защита.
6. **▶ Открыть живой пример** — кнопка на соответствующий экран.

Контент берётся и адаптируется из уже лежащего в репо `docs/security-guide/` (9 модулей на русском) — не пишем с нуля.

## 8. Тема и брендинг

- ETM-палитра воссоздаётся локально в `lib/theme.ts` (antd tokens) + `styles/_tokens.scss` (SCSS-переменные) — **одни и те же значения**, чтобы antd и SCSS не разъезжались.
- Базовый `colorPrimary` — ETM-синий (плейсхолдер ~`#0A5AD3`/`#1A6FE0`, **тюнится одной строкой**; точное значение подставим по скриншоту живого приложения, если пользователь его даст).
- Логотип — локальный SVG-плейсхолдер (не тянем `cdn.etm.ru` спрайт). Иконки — `@ant-design/icons`.
- Каркас: `Layout` → `Header` (лого + `Menu mode="horizontal"`) + `Sider collapsible` (`Menu mode="inline"`) + `Content`. Русские подписи меню как в оригинале.

## 9. Как это запускается (без VPN)

```bash
npm install      # только публичные пакеты
npm run dev      # http://localhost:3000
```

- Нет обращений к `*.etm.ru`, нет Docker-прокси, нет правки hosts.
- Данные сидятся в локальный SQLite при первом старте (тестовые пользователи, заказы, факторинг-заявки, статьи с «полезной нагрузкой» для stored XSS).
